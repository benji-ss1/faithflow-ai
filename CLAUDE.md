# CLAUDE.md — Working standard for AI-assisted work on this repo

**START HERE every session:** read [docs/AI_HANDOFF.md](docs/AI_HANDOFF.md) — the fast onboarding for how this repo ships (renderer→Vercel/reload vs Electron→DMG vs parser→Fly), how work is done (the loop + 3-agent review), the current offline-first epic status, and the traps. Then this file for the rules.

Before you make any non-trivial change, read [docs/AGENT_WORKFLOW.md](docs/AGENT_WORKFLOW.md).

## Non-negotiables

1. **The loop is the standard.** Plan → Build → Review → Fix → Re-test → Ship → Report. Skipping steps produces provisional work, not done work.

2. **Three review agents, always, in parallel** for anything > 100 LOC or touching auth, data, church_id, AI, or output channels: reviewer + security + stress. Spawn them in one message with `run_in_background: true`. Full prompt templates in `docs/AGENT_WORKFLOW.md`.

3. **Every finding must be tagged 🔴/🟡/🟢.** No unranked prose. No soft passes.

4. **Every checkpoint gets a status block.** Copy the template from `docs/AGENT_WORKFLOW.md#checkpoint-template`. If you can't fill in a field, that step isn't done.

5. **Church_id scoping is mandatory** on every DB write and every semantic/vector query. Only exception: the Bible library, documented in `src/lib/server/bible.ts:12-17`. New paths need an adversarial test in `test/adversarial/`.

6. **AI provider is Groq** (llama-3.3-70b-versatile) via `src/lib/ai-helpers.ts`. Graceful degradation when key missing. No fallbacks to other providers without explicit sign-off.

7. **Songs auto-project ONLY at ≥70% AI-detection confidence** (`SONG_AUTOLIVE_CONFIDENCE` in `ProOperatorShell.tsx`) — originally 85% (2026-07-22 sign-off), lowered to 70% on 2026-07-26 with a fresh user sign-off after field-test data showed most real detections landed in the 60-84% stage-only band and operators were missing the required G keypress. Below 70%, a human confirm keypress ("G") is required; nothing below `SONG_STAGE_CONFIDENCE` (60%) does anything but sit as a passive chip. Auto-live at ≥70% carries the same anti-replay/min-gap guardrails as Bible's AUTO-approve path (session-persisted fired-key map, min-gap cooldown). **2026-07-23 refinement (user-approved):** anti-replay guards (Bible `AUTO_FIRED_SESSION_KEY` sessionStorage map + song `SONG_AUTO_FIRED_SESSION_KEY` map + `stagedOrHandledRef` redetect cooldown) now BYPASS when a DIFFERENT reference/song is currently live — that's a legitimate preacher/worship-leader back-and-forth swap (Matt 5:5 → Gen 4:4 → back to Matt 5:5, or Song A → Song B → back to Song A). Same-reference echo suppression is retained. **2026-07-26 chip-click carve-out (user-approved):** direct operator click on a song chip in the AI chips bar fires slide 1 to live regardless of confidence — direct operator intent is trusted (mirrors the SongsBrowser slide click). **2026-07-26 AUTO-toggle decoupling (user-approved):** song auto-fire is no longer gated on the operator's AUTO/MANUAL autopilot toggle — the ≥70% policy applies unconditionally. The AUTO toggle now only controls Bible auto-approve (its original purpose). Rationale: field report where operator in MANUAL mode had a legitimate 87% song detection that silently no-op'd because the AUTO gate blocked the entire song path. Songs already have their own auth model (per-confidence-tier + G-key), so the extra AUTO gate was pure friction. Do not lower `SONG_AUTOLIVE_CONFIDENCE` further, drop below 65% (the current hard floor for the "if we ever go lower" conversation), or extend zero-click auto-project to other content types without new explicit sign-off. **2026-07-29 translation-switch carve-out (user-approved):** voice-detected Bible translation switches in AUTO mode may re-render the CURRENTLY-LIVE scripture slide in the new translation (same verse, different text) — explicitly specified in the JPD Fix-6 requirements ("if a verse is currently displayed, re-fetch it in the new translation and update the projector"). Confined to the Bible AUTO envelope; never fires when the live slide is not scripture; ambiguous translation names require strong switch-intent phrasing. **2026-07-30 same-reference micro-cooldown (user-approved):** Bible anti-replay for AUTO-approve is lifted to a 3s micro-cooldown per reference (was: session-persistent 5-minute suppression). Rationale: preachers legitimately repeat "Psalm 23:4" throughout a sermon and each repeat should re-project. The 3s window still absorbs same-utterance duplicate detections (Deepgram interim → final → whisper cascade). All other CLAUDE.md rule-7 constraints (SONG_AUTOLIVE_CONFIDENCE=70, AUTO-toggle scope, chip-click carve-out, translation-switch carve-out) unchanged. Implementation lives in `src/lib/bible-antireplay.ts` (pure helper, directly unit-testable). Song anti-replay (`SONG_AUTO_FIRED_SESSION_KEY`) stays at 5 minutes — a worship set doesn't come back mid-service the way a preached verse does. **2026-07-30 translation-coverage broadening (user-approved):** the spoken translation-switch detector now recognises the full 24-code English translation list (KJV, NKJV, NIV, ESV, NLT, NASB, ASV, WEB, AMP, MSG, CSB, HCSB, RSV, NRSV, CEV, GNT, ISV, NET, YLT, DRA, WBS, BBE, DARBY, plus GEN1599/DRC legacy) and UNAMBIGUOUS full names now fire on ANY mention — no switch-intent verb required — so any mention of "the New International" or "Holman" triggers a switch. Ambiguous names (WEB, AMP, MSG, ASV, NET, "the message", "amplified") STILL require intent-gating; the "caught in a web of sin" / "the message of hope" false-positive protection MUST survive. Requests for a code the DB doesn't carry surface a "not available" toast and DO NOT mutate the session translation — see `docs/BIBLE_TRANSLATIONS.md` for the ESV.org free-tier API scaffold (`src/lib/server/esv-fallback.ts`, env-gated on `ESV_API_KEY`, dormant until wired). **2026-08-14 song-confidence RAISE (user-approved, supersedes the 2026-07-26 lowering):** field feedback was that songs over-suggest and auto-project too eagerly (many low-confidence chips constantly popping during worship, occasional wrong-song projection). Song policy is now MORE conservative, mirroring the Bible tiering shape but with a higher auto bar: `SONG_AUTOLIVE_CONFIDENCE=85` (auto-project ONLY at ≥85%), `SONG_STAGE_CONFIDENCE=70` (70-84% = manual chip in the AI-chip "golden section" / G-key; nothing below 70% surfaces at all). The auto bar is higher than Bible's 75% ON PURPOSE because songs share lyrics with each other and with sung worship. Additionally, even at ≥85% a song auto-projects ONLY if it beats the next-best DIFFERENT candidate by `SONG_DISAMBIG_MARGIN=12` points — when two songs match the words almost equally the engine can't be sure which one it is, so it downgrades to a manual chip rather than risk the wrong song (all three constants in `operatorConstants.ts`). The old "hard floor 65%" note is retired; 70/85 is the new floor. Do not lower these without fresh field data + sign-off. STILL OPEN (deeper detection work, not just thresholds): distinguishing spoken Bible-verse reading from song lyrics, and robust similar-song disambiguation beyond the top-2 margin — tracked for the song-detection engine (`src/lib/ai-detection/song-match.ts`). **2026-08-18 verse-nav split (user-approved):** MANUAL Verse ◀ / ▶ buttons remain PREVIEW-ONLY (2026-08-16 directive — advance the centre panel, don't project). VOICE "next verse"/"continue"/"go back" commands now PROJECT IMMEDIATELY again (instant hard cut, no transition flicker) — they dispatch the same `presentflow:bible-next/prev` internal events but with a `{ live: true }` payload, so `applyAdvancedVerse(..., live)` calls `onSendSlideToLive`. This restores fast voice auto-advance that the 2026-08-16 preview-only change had inadvertently disabled by coupling voice to the manual event. Voice path keeps its confidence floor (≥70), `BIBLE_SLIDE_FLOOR_MS` and `bibleCooldownUntilRef` gating. Needs field verification (mic + projector) before relying on it in a service. **2026-08-19 fade-pulse fix (user-approved, field video):** a verse HELD on the projector was fading out/in on a loop because (a) the AI kept re-firing the same on-screen verse every time it heard it re-preached, and (b) `TransitionWrapper` restarted its CSS enter animation whenever the operator's published `transition` field changed value (AI_AUTO_TRANSITION ↔ configured spec alternated on every OutputState re-post) even though the slide was byte-identical. Two fixes: (1) `TransitionWrapper` now FREEZES the enter animation at mount (per content-identity), so a changed `transition` prop on already-mounted content can never replay it — only a genuine content change (new identity → remount) animates. (2) `decideBibleAutoFire` now SUPPRESSES any auto-fire whose target is ALREADY the live slide (reason `suppress:already-live`), mirroring the song path's same-song-already-live skip — a DIFFERENT ref (or non-scripture) live still fires immediately (swap/swap-back), voiceCommand still bypasses. This SUPERSEDES the 2026-07-30 "each repeat re-projects" behaviour for the case where the verse is still on screen: re-projecting an on-screen verse only replays the transition (the pulse), so it's now skipped; a restatement after moving AWAY still re-projects (different-ref path). The former firedMap / 3s micro-cooldown / forceLive gating in `decideBibleAutoFire` is now vestigial (only ever reached in the same-ref-live branch). Content-identity for all three outputs (`/live`, `/stage`, `/livestream`) is consolidated in `broadcast.ts → slideOutputIdentity` (must stay content-only — no fontScale/zone/appearance/timestamps, or the pulse returns). Tests: `test/bible-antireplay.test.ts` (21 pass).

8. **Same-machine BroadcastChannel is the primary sync path.** Supabase Realtime is additive fan-out. New sync features must preserve the same-machine zero-latency path.

9. **Speech→scripture must handle African-preacher accents and ASR mishearings, not just clean input.** The user base is African (largely Nigerian/RCCG) churches; test the parser against real accented transcripts, never idealized text. `src/lib/bible-parser.ts` owns this: (a) `repairNumberHomophones()` fixes TH-fronting (Deepgram hears "three"→"tree", "third"→"tird", "thirty"→"tirty", "thousand"→"tousand") BEFORE any number pattern runs — extend it, with a guard, when new mishearings surface (e.g. "tree" is skipped before "of" so "tree of life" isn't read as "3"); (b) `fuzzyBookMatch()` (edit-distance) catches near-miss book names ("filippians", "corintians", "ecclesiastis") and is wired into live parsing via the `fuzzy_book_ch_verse` pattern — gated to a chapter:verse shape + low confidence + semantic fallback so it can't false-fire on ordinary speech. All 66 books must always resolve via `knownBook()` (there's a coverage check pattern in the parser tests). When a real transcript reveals a miss, fix it case-by-case AND consider whether it's a systematic accent pattern worth a general rule.

10. **AI-detection latency is a product requirement: detections must track live speech, not lag it.** The predictive path lives in `scripts/audio-server.ts`'s interim handler: it early-fires an `interim_final_candidate` the moment an interim already parses to a reference (`parseReferences(text).length > 0`, gated by a cheap numeric pre-check to keep the hot path lean) OR clears a loosened generic gate (≥3 words, ≥0.75 confidence), rather than waiting for Deepgram's finalized utterance (~200ms endpointing + network). Don't raise those gates without cause; if anything, push detection earlier. Keep `endpointing=100` — the field-tuned floor as of 2026-07-24 (progression: 10ms broke utterances into fragments, 50ms broke, 75ms was edge, 150ms felt slow, 100ms is safe; see the comment in `scripts/audio-server.ts`). Do not raise it (a request to go to 300ms was declined 2026-07-25) and do not go below 100 without a fresh field test. Client dedupes interim candidates against the eventual final by reference key.

11. **Sermon-search RAG (chunk-level) ingestion runs SERVER-SIDE ONLY.** `src/lib/server/sermon-rag.ts` chunks + embeds transcripts into `sermon_chunks` (pgvector, church-scoped). The embedding model (`@xenova/transformers`, ~90MB) does NOT load in every dev environment, so ingestion cannot be verified locally — it runs via `after()` on live-session end, the admin `POST /api/sermon/backfill` (paste a past transcript), and the daily `/api/cron/backfill-sermons` cron (drains any plan with segments-but-no-chunks; bounded + idempotent). Never bulk-import scraped/ASR lyric text as song content, and never hardcode transcripts (esp. worship lyrics) into the repo — load historical transcripts through the backfill route.

## Where things live

- `docs/AGENT_WORKFLOW.md` — the loop + agent prompts + checkpoint template
- `src/lib/db/schema.ts` — Drizzle schema; church_id FK on every tenant-owned table
- `src/lib/server/*` — server-only helpers; import boundary between DB and routes
- `src/lib/ai-detection/*` — unified detection engine (P5A); no web lyric scraping
- `src/lib/realtime.ts` — cross-device output channel
- `src/lib/broadcast.ts` — BroadcastChannel same-machine primitive
- `src/lib/actions.ts` — every server action; auth-gated + church-scoped
- `test/adversarial/` — cross-church leakage + prod invariants; run before every ship
- `scripts/audio-server.ts` — Fly.io-hosted WebSocket bridge (not Vercel)

## Deploy runbook

- Next.js app → Vercel (git push to main triggers auto-deploy)
- Audio bridge → Fly.io (`./scripts/deploy.sh audio`)
- DB + Storage → Supabase (Postgres w/ pgvector + S3-compatible storage)
- See `DEPLOY.md` for the full runbook.

## When you hit unknowns

- Missing hardware (mic, projector, mixer): document as untestable, do NOT claim tested.
- Missing external service (Fly not up, Groq key missing): document as known gap; prove graceful degradation.
- Missing acceptance criteria in the ask: state them explicitly BEFORE running. No retroactive softening.
