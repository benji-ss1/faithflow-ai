# CLAUDE.md — Working standard for AI-assisted work on this repo

**START HERE every session:** read [docs/AI_HANDOFF.md](docs/AI_HANDOFF.md) — the fast onboarding for how this repo ships (renderer→Vercel/reload vs Electron→DMG vs parser→Fly), how work is done (the loop + 3-agent review), the current offline-first epic status, and the traps. Then this file for the rules.

Before you make any non-trivial change, read [docs/AGENT_WORKFLOW.md](docs/AGENT_WORKFLOW.md).

## Non-negotiables

1. **The loop is the standard.** Plan → Build → Review → Fix → Re-test → Ship → Report. Skipping steps produces provisional work, not done work.

2. **Three review agents, always, in parallel** for anything > 100 LOC or touching auth, data, church_id, AI, or output channels: reviewer + security + stress. Spawn them in one message with `run_in_background: true`. Full prompt templates in `docs/AGENT_WORKFLOW.md`.

3. **Every finding must be tagged 🔴/🟡/🟢.** No unranked prose. No soft passes.

4. **Every checkpoint gets a status block.** Copy the template from `docs/AGENT_WORKFLOW.md#checkpoint-template`. If you can't fill in a field, that step isn't done.

5. **Church_id scoping is mandatory** on every DB write and every semantic/vector query. Only exception: the Bible library, documented in `src/lib/server/bible.ts:12-17`. New paths need an adversarial test in `test/adversarial/`.

6. **AI provider is Groq** (llama-3.3-70b-versatile) via `src/lib/ai-helpers.ts`. Graceful degradation when key missing. No fallbacks to other providers without explicit sign-off.

7. **Songs auto-project ONLY at ≥70% AI-detection confidence** (`SONG_AUTOLIVE_CONFIDENCE` in `ProOperatorShell.tsx`) — originally 85% (2026-07-22 sign-off), lowered to 70% on 2026-07-26 with a fresh user sign-off after field-test data showed most real detections landed in the 60-84% stage-only band and operators were missing the required G keypress. Below 70%, a human confirm keypress ("G") is required; nothing below `SONG_STAGE_CONFIDENCE` (60%) does anything but sit as a passive chip. Auto-live at ≥70% carries the same anti-replay/min-gap guardrails as Bible's AUTO-approve path (session-persisted fired-key map, min-gap cooldown). **2026-07-23 refinement (user-approved):** anti-replay guards (Bible `AUTO_FIRED_SESSION_KEY` sessionStorage map + song `SONG_AUTO_FIRED_SESSION_KEY` map + `stagedOrHandledRef` redetect cooldown) now BYPASS when a DIFFERENT reference/song is currently live — that's a legitimate preacher/worship-leader back-and-forth swap (Matt 5:5 → Gen 4:4 → back to Matt 5:5, or Song A → Song B → back to Song A). Same-reference echo suppression is retained. **2026-07-26 chip-click carve-out (user-approved):** direct operator click on a song chip in the AI chips bar fires slide 1 to live regardless of confidence — direct operator intent is trusted (mirrors the SongsBrowser slide click). **2026-07-26 AUTO-toggle decoupling (user-approved):** song auto-fire is no longer gated on the operator's AUTO/MANUAL autopilot toggle — the ≥70% policy applies unconditionally. The AUTO toggle now only controls Bible auto-approve (its original purpose). Rationale: field report where operator in MANUAL mode had a legitimate 87% song detection that silently no-op'd because the AUTO gate blocked the entire song path. Songs already have their own auth model (per-confidence-tier + G-key), so the extra AUTO gate was pure friction. Do not lower `SONG_AUTOLIVE_CONFIDENCE` further, drop below 65% (the current hard floor for the "if we ever go lower" conversation), or extend zero-click auto-project to other content types without new explicit sign-off. **2026-07-29 translation-switch carve-out (user-approved):** voice-detected Bible translation switches in AUTO mode may re-render the CURRENTLY-LIVE scripture slide in the new translation (same verse, different text) — explicitly specified in the JPD Fix-6 requirements ("if a verse is currently displayed, re-fetch it in the new translation and update the projector"). Confined to the Bible AUTO envelope; never fires when the live slide is not scripture; ambiguous translation names require strong switch-intent phrasing. **2026-07-30 same-reference micro-cooldown (user-approved):** Bible anti-replay for AUTO-approve is lifted to a 3s micro-cooldown per reference (was: session-persistent 5-minute suppression). Rationale: preachers legitimately repeat "Psalm 23:4" throughout a sermon and each repeat should re-project. The 3s window still absorbs same-utterance duplicate detections (Deepgram interim → final → whisper cascade). All other CLAUDE.md rule-7 constraints (SONG_AUTOLIVE_CONFIDENCE=70, AUTO-toggle scope, chip-click carve-out, translation-switch carve-out) unchanged. Implementation lives in `src/lib/bible-antireplay.ts` (pure helper, directly unit-testable). Song anti-replay (`SONG_AUTO_FIRED_SESSION_KEY`) stays at 5 minutes — a worship set doesn't come back mid-service the way a preached verse does. **2026-07-30 translation-coverage broadening (user-approved):** the spoken translation-switch detector now recognises the full 24-code English translation list (KJV, NKJV, NIV, ESV, NLT, NASB, ASV, WEB, AMP, MSG, CSB, HCSB, RSV, NRSV, CEV, GNT, ISV, NET, YLT, DRA, WBS, BBE, DARBY, plus GEN1599/DRC legacy) and UNAMBIGUOUS full names now fire on ANY mention — no switch-intent verb required — so any mention of "the New International" or "Holman" triggers a switch. Ambiguous names (WEB, AMP, MSG, ASV, NET, "the message", "amplified") STILL require intent-gating; the "caught in a web of sin" / "the message of hope" false-positive protection MUST survive. Requests for a code the DB doesn't carry surface a "not available" toast and DO NOT mutate the session translation — see `docs/BIBLE_TRANSLATIONS.md` for the ESV.org free-tier API scaffold (`src/lib/server/esv-fallback.ts`, env-gated on `ESV_API_KEY`, dormant until wired). **2026-08-14 song-confidence RAISE (user-approved, supersedes the 2026-07-26 lowering):** field feedback was that songs over-suggest and auto-project too eagerly (many low-confidence chips constantly popping during worship, occasional wrong-song projection). Song policy is now MORE conservative, mirroring the Bible tiering shape but with a higher auto bar: `SONG_AUTOLIVE_CONFIDENCE=85` (auto-project ONLY at ≥85%), `SONG_STAGE_CONFIDENCE=70` (70-84% = manual chip in the AI-chip "golden section" / G-key; nothing below 70% surfaces at all). The auto bar is higher than Bible's 75% ON PURPOSE because songs share lyrics with each other and with sung worship. Additionally, even at ≥85% a song auto-projects ONLY if it beats the next-best DIFFERENT candidate by `SONG_DISAMBIG_MARGIN=12` points — when two songs match the words almost equally the engine can't be sure which one it is, so it downgrades to a manual chip rather than risk the wrong song (all three constants in `operatorConstants.ts`). The old "hard floor 65%" note is retired; 70/85 is the new floor. Do not lower these without fresh field data + sign-off. STILL OPEN (deeper detection work, not just thresholds): distinguishing spoken Bible-verse reading from song lyrics, and robust similar-song disambiguation beyond the top-2 margin — tracked for the song-detection engine (`src/lib/ai-detection/song-match.ts`). **2026-08-18 verse-nav split (user-approved):** MANUAL Verse ◀ / ▶ buttons remain PREVIEW-ONLY (2026-08-16 directive — advance the centre panel, don't project). VOICE "next verse"/"continue"/"go back" commands now PROJECT IMMEDIATELY again (instant hard cut, no transition flicker) — they dispatch the same `presentflow:bible-next/prev` internal events but with a `{ live: true }` payload, so `applyAdvancedVerse(..., live)` calls `onSendSlideToLive`. This restores fast voice auto-advance that the 2026-08-16 preview-only change had inadvertently disabled by coupling voice to the manual event. Voice path keeps its confidence floor (≥70), `BIBLE_SLIDE_FLOOR_MS` and `bibleCooldownUntilRef` gating. Needs field verification (mic + projector) before relying on it in a service. **2026-08-19 fade-pulse fix (user-approved, field video):** a verse HELD on the projector was fading out/in on a loop because (a) the AI kept re-firing the same on-screen verse every time it heard it re-preached, and (b) `TransitionWrapper` restarted its CSS enter animation whenever the operator's published `transition` field changed value (AI_AUTO_TRANSITION ↔ configured spec alternated on every OutputState re-post) even though the slide was byte-identical. Two fixes: (1) `TransitionWrapper` now FREEZES the enter animation at mount (per content-identity), so a changed `transition` prop on already-mounted content can never replay it — only a genuine content change (new identity → remount) animates. (2) `decideBibleAutoFire` now SUPPRESSES any auto-fire whose target is ALREADY the live slide (reason `suppress:already-live`), mirroring the song path's same-song-already-live skip — a DIFFERENT ref (or non-scripture) live still fires immediately (swap/swap-back), voiceCommand still bypasses. This SUPERSEDES the 2026-07-30 "each repeat re-projects" behaviour for the case where the verse is still on screen: re-projecting an on-screen verse only replays the transition (the pulse), so it's now skipped; a restatement after moving AWAY still re-projects (different-ref path). The former firedMap / 3s micro-cooldown / forceLive gating in `decideBibleAutoFire` is now vestigial (only ever reached in the same-ref-live branch). Content-identity for all three outputs (`/live`, `/stage`, `/livestream`) is consolidated in `broadcast.ts → slideOutputIdentity` (must stay content-only — no fontScale/zone/appearance/timestamps, or the pulse returns). Tests: `test/bible-antireplay.test.ts` (21 pass). **2026-08-20 doc reconciliation:** the live song constants are `SONG_AUTOLIVE_CONFIDENCE=90` / `SONG_STAGE_CONFIDENCE=80` (raised from 85/70 on 2026-08-16, see the sign-off comments in `operatorConstants.ts`) — earlier prose in this rule that says 85/70 is superseded by those. **2026-08-20 Worship/Preacher service mode (user-approved):** a new operator-facing 3-way toggle (`ServiceMode = "auto"|"worship"|"preacher"`, top bar, session-scoped in `OperatorConsole`, threaded via `getDetectContext` → `DetectAllContext` → `detectAll`) BIASES detection only — it never touches capture, the mic board, or the fragile auto-fire gates. It acts purely by re-weighting the confidences those gates already read, so a de-weighted detection just lands in the manual-chip tier: (a) **worship** biases AUTO-projection to the setlist — setlist songs get a SURFACING nudge and stay auto-eligible while OFF-plan songs are held at chip-tier (NOT dropped, so a spontaneous unplanned song still surfaces for one-tap firing); `restrictToPlan` is a no-op when the plan has no songs (full-library fallback). The setlist nudge (2026-08-20 field directive "why do I have to push it live?") is allowed to carry a GENUINE setlist match over the 90 auto bar so it zero-click projects — guarded two ways: it only applies when the pre-boost lyric/title score ≥ `WORSHIP_BOOST_MIN_SCORE=35` (ASR-noise grazes can't be boosted to auto) and the top-2 disambiguation margin still downgrades near-equal setlist pairs to a manual chip. It also HOLDS detected scripture at chip-tier (`WORSHIP_SCRIPTURE_CAP=74`, applied AUTHORITATIVELY in `useAudioStream.runDetectAll` after `blendScripture` re-blends, with navigation commands EXEMPT so voice "next verse" still projects); (b) **preacher** caps songs at `PREACHER_SONG_CAP=89` so speech never zero-clicks a song, scripture untouched; (c) **auto** (default) is a verified pure no-op. Both caps are pinned one-below the live bars by a drift-guard test. Neither mode LOWERS any auto-fire bar. Tests: `test/service-mode.test.ts` (8 pass). **2026-08-30 verse-repeat deeper fix (user-directed, field-test PENDING):** two changes to stop a re-preached ALREADY-LIVE verse from disturbing the operator. (1) **Preview/live no-op (V1):** the routing-effect async-lookup block (`ProOperatorShell.tsx` ~2438-2452) decided the projector re-send from a raw TEXT-identity check and synced the center/preview panel UNCONDITIONALLY — so re-hearing a held verse churned the operator's staged preview (and could re-pulse the projector on a formatting/translation body difference). It now decides BOTH from the REFERENCE via the pure `resolvedDetectionAction(liveSlide, target)` in `bible-antireplay.ts` (`{send,syncPreview}` both false iff the target ref is already live) — re-hearing the on-screen verse is a COMPLETE no-op; a different ref (swap-back/next/new passage) still projects + syncs. (2) **Silence-advance repeat-hold (V2):** the Part 2c silence+coverage auto-advance (`ProOperatorShell.tsx` ~3082-3097) advanced on "current verse covered + 2.5s silence" with NO next-verse evidence, so a preacher re-reading/repeating the live verse and pausing jumped the screen forward. It now ALSO requires `matchNextSlide(recentWords, nextTEXT).consecutiveMatches >= BIBLE_NEXT_EVIDENCE_MIN` (=3, `operatorConstants.ts`). CRITICAL: the evidence matches the verse TEXT ONLY — the `"17 "` number prefix is never spoken, and feeding the numbered body scored 0 for continuous reading (would have stranded genuine advance). This REMOVES proactive-advance-on-pause-alone: the screen now advances when the NEXT verse is actually being read, not merely on a pause after the current one — deliberate, matches the repeat-heavy base. Carve-outs untouched: swap-back (different-ref path), real "next verse" voice command (`presentflow:bible-next {live:true}`), and the 2026-07-29 translation-switch (separate `applyTranslationSwitch` effect with `force:true`). Renderer-only → Vercel (no Fly, no DMG). Tests: `test/bible-antireplay.test.ts` (29 pass, +8 for `resolvedDetectionAction`/`liveGuardText`), `test/bible-silence-advance.test.ts` (5 pass). **MUST be field-verified on real mic + projector** (repeat-heavy passage holds AND a sequential read-through still advances) before relying on it live — like every prior auto-advance change. KNOWN LIMITS (non-blocking, backstopped by the content-identity skip for the projector): with reference-display OFF the preview can still churn on a re-hearing (guard falls back to unparseable body text); and "Song of Solomon"/"Song of Songs" defeat the single-token book regex in `parseLiveScriptureRef`. **2026-08-30 Context Engine — spoken-context song cap (Phase 1, DORMANT behind a flag):** a new deterministic speech classifier (`src/lib/ai-detection/context-lexicons.ts` + `context-engine.ts`, grounded in the real JPD service transcript per rule 9) scores each utterance into six classes (prayer / scripture-reading / preaching / worship / nav / announcement) with EWMA smoothing + hysteresis. When the rolling context says we're confidently in a SPOKEN moment (`isSpokenContext` — a spoken class, conf ≥ 0.30, AND worship-EWMA < 0.30), `detectAll` caps co-occurring song/lyric matches to `SPOKEN_SUGGEST_CAP=84` (chip-tier, in the 80-89 band, below the live `SONG_AUTOLIVE_CONFIDENCE=90` auto bar) — so a spoken worship-adjacent phrase ("in the mighty name of Jesus", "king of kings") can't zero-click a song. Mirrors the existing verse-vs-song `SUGGEST_CAP=84` (never HIDES a song), exempts an explicit "let's sing" cue / exact-title trigger. Wired in `useAudioStream`: the cap uses the ACCUMULATED prior-utterance snapshot, and after each `detectAll` the lyric-match score + scripture/nav signals are folded back so sustained real worship lifts the worship guard and is NOT capped (the lyric-match score — not `musicSuspected`, which is anti-correlated with clean singing — is the load-bearing worship signal; the adversarial gate proved `musicSuspected`-only capped clean-sung testimony lyrics). **FLAG-GATED OFF by default** (`NEXT_PUBLIC_CONTEXT_ENGINE=1` or localStorage `pro.contextEngine.v1`): when off, `ctx.context` is undefined → the cap is a provable no-op (parity test-locked), so shipping to main is safe/dormant. **DO NOT enable on a live service until it's field-verified on real worship + preaching audio** — the residual risk is the FIRST sung line of a set (before the lyric signal accumulates) being chip-capped (bounded: one operator tap, never hidden, never mis-projected). No changelog entry until the flag is flipped on for testers (no user-visible change while dormant). **2026-08-30 Context Engine Phase 2 — story-context voice-nav suppression (WIRED, same dormant flag):** `isStoryContext` is now consumed. `useAudioStream` surfaces `contextIsStory` on the audio state (from the rolling snapshot's `isStoryContext`, set only on change; only ever true when the engine flag is on). `ProOperatorShell`'s two voice-nav dispatch effects use it: during confident STORY/PREACHING, the interim early-fire suppresses MID-confidence relative-nav (<85) and the final path raises the immediate-fire floor to 85 (`navFireFloor = contextIsStory ? 85 : 70`), so a soft "continue"/"go on to next" (70-84) becomes a one-tap CONFIRM toast instead of stepping the verse mid-story — while ANCHORED nav ("next verse"=85, "previous verse"=90, etc.) fires exactly as before. 85 sits on a natural cliff in `context-parser.ts` (no pattern scores 81-84). 8. **Same-machine BroadcastChannel is the primary sync path.** Supabase Realtime is additive fan-out. New sync features must preserve the same-machine zero-latency path.

9. **Speech→scripture must handle African-preacher accents and ASR mishearings, not just clean input.** The user base is African (largely Nigerian/RCCG) churches; test the parser against real accented transcripts, never idealized text. `src/lib/bible-parser.ts` owns this: (a) `repairNumberHomophones()` fixes TH-fronting (Deepgram hears "three"→"tree", "third"→"tird", "thirty"→"tirty", "thousand"→"tousand") BEFORE any number pattern runs — extend it, with a guard, when new mishearings surface (e.g. "tree" is skipped before "of" so "tree of life" isn't read as "3"); (b) `fuzzyBookMatch()` (edit-distance) catches near-miss book names ("filippians", "corintians", "ecclesiastis") and is wired into live parsing via the `fuzzy_book_ch_verse` pattern — gated to a chapter:verse shape + low confidence + semantic fallback so it can't false-fire on ordinary speech. All 66 books must always resolve via `knownBook()` (there's a coverage check pattern in the parser tests). When a real transcript reveals a miss, fix it case-by-case AND consider whether it's a systematic accent pattern worth a general rule.

10. **AI-detection latency is a product requirement: detections must track live speech, not lag it.** The predictive path lives in `scripts/audio-server.ts`'s interim handler: it early-fires an `interim_final_candidate` the moment an interim already parses to a reference (`parseReferences(text).length > 0`, gated by a cheap numeric pre-check to keep the hot path lean) OR clears a loosened generic gate (≥3 words, ≥0.75 confidence), rather than waiting for Deepgram's finalized utterance (~200ms endpointing + network). Don't raise those gates without cause; if anything, push detection earlier. Keep `endpointing=100` — the field-tuned floor as of 2026-07-24 (progression: 10ms broke utterances into fragments, 50ms broke, 75ms was edge, 150ms felt slow, 100ms is safe; see the comment in `scripts/audio-server.ts`). Do not raise it (a request to go to 300ms was declined 2026-07-25) and do not go below 100 without a fresh field test. Client dedupes interim candidates against the eventual final by reference key.

11. **Sermon-search RAG (chunk-level) ingestion runs SERVER-SIDE ONLY.** `src/lib/server/sermon-rag.ts` chunks + embeds transcripts into `sermon_chunks` (pgvector, church-scoped). The embedding model (`@xenova/transformers`, ~90MB) does NOT load in every dev environment, so ingestion cannot be verified locally — it runs via `after()` on live-session end, the admin `POST /api/sermon/backfill` (paste a past transcript), and the daily `/api/cron/backfill-sermons` cron (drains any plan with segments-but-no-chunks; bounded + idempotent). Never bulk-import scraped/ASR lyric text as song content, and never hardcode transcripts (esp. worship lyrics) into the repo — load historical transcripts through the backfill route.

## Where things live

- `docs/AGENT_WORKFLOW.md` — the loop + agent prompts + checkpoint template

## When you hit unknowns

- Missing hardware (mic, projector, mixer): document as untestable, do NOT claim tested.
- Missing external service (Fly not up, Groq key missing): document as known gap; prove graceful degradation.
- Missing acceptance criteria in the ask: state them explicitly BEFORE running. No retroactive softening.
